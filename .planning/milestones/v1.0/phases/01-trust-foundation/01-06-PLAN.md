<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Expo push service → device | Notifications are informational; they must not themselves grant access |
| device → backend (push-token) | Token saved against the authenticated user only |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-06-01 | Spoofing | forged approval push granting access | high | mitigate | notification tap only triggers getIdToken(true); real access derives from the signed isVerified custom claim set by the backend (D-08), not the push payload |
| T-06-02 | Tampering | registering another user's push token | medium | mitigate | push-token endpoint keys on `req.user.uid` from the verified token; a caller can only set their own token |
| T-06-03 | Denial of Service | push flooding | low | accept | expo-server-sdk handles rate limiting/batching (600/sec); volume is admin-driven and low for MVP |
</threat_model>
