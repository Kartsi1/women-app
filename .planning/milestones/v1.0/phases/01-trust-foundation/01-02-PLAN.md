<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| device → Firebase Auth | Email/password auth handled entirely by Firebase; app never stores a password |
| device → backend | Firebase ID token sent as Bearer; backend verifies |
| navigation gate | Client-side gate is UX only — real enforcement is the backend `requireVerified` + custom claim |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-01 | Elevation | navigation gate bypass | high | mitigate | client gate is defense-in-depth; authoritative gate is backend `requireVerified` (Plan 01) — no protected data is served to an unverified token |
| T-02-02 | Information Disclosure | EXPO_PUBLIC_FIREBASE_* keys | low | accept | Firebase Web config keys are public by design; Storage/Firestore rules enforce access, not key secrecy |
| T-02-03 | Spoofing | fake approval push | medium | mitigate | notification tap only triggers a token refresh; actual verified state comes from the signed custom claim, not the notification payload (D-08) |
| T-02-04 | Tampering | session persistence | low | mitigate | Firebase JS SDK manages token refresh/expiry via AsyncStorage; app does not hand-roll session storage |
</threat_model>
