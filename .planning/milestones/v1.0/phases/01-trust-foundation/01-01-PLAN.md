<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| mobile client → backend API | Untrusted Firebase ID token crosses here; must be cryptographically verified, not decoded |
| backend → MongoDB | User identity written from verified-token claims only |
| backend → Firebase Admin | Service account credentials loaded from env, never from client |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-01 | Spoofing | POST /api/auth/register | high | mitigate | `getAuth().verifyIdToken()` cryptographically verifies the token (rotating keys) — no manual JWT decode (RESEARCH Don't-Hand-Roll) |
| T-01-02 | Tampering | User.email / uid | medium | mitigate | email + uid taken from decoded token `req.user`, never from request body |
| T-01-03 | Information Disclosure | FIREBASE_SERVICE_ACCOUNT_JSON | high | mitigate | stored in `.env` (gitignored); `.env.example` holds an empty placeholder only; never committed |
| T-01-04 | Elevation | requireVerified bypass | high | mitigate | `isVerified` derived from signed custom claim in the token, defaults false; verified-only routes gated by `requireVerified` |
| T-01-SC | Tampering | npm installs (firebase-admin, multer, expo-server-sdk) | high | mitigate | all three Approved in RESEARCH Package Legitimacy Audit (SUS verdicts are "too-new", not hallucinated); pinned versions |
</threat_model>
