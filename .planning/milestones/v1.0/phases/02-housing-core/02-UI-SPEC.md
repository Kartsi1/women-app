# Phase 2 — Housing Core: UI Design Contract

> Visual and interaction contract for Phase 2 frontend screens.
> Generated by gsd-ui-researcher. Verified by gsd-ui-checker.
>
> **Requirements covered:** LIST-01..05, REQT-01..04, MSG-01..05
>
> **Safety principle:** Exact address MUST remain hidden until the host accepts the stay
> request. Every listing detail screen must display a safety chip for non-accepted guests.
> This is a hard UI constraint derived from LIST-03 and REQT-03.

## Spacing Scale

Declared values (multiples of 4 only):

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon gaps, badge padding, dot indicators |
| sm | 8px | Inline element spacing, chip padding, tight card internal gaps |
| md | 16px | Default element spacing, container horizontal padding, input padding |
| lg | 24px | Section padding, screen edge padding (matches Phase 1 container padding) |
| xl | 32px | Title bottom margin, major card gaps |
| 2xl | 48px | Screen top padding (matches Phase 1 paddingTop), major section breaks |
| 3xl | 64px | Page-level bottom padding for floating send button clearance |

**Exceptions:**
- Minimum touch target: 44×44dp — all interactive icons (map controls, close buttons, send icon)
- Chat input row: min-height 48px
- Floating action button (map — "List your space"): 56×56dp
- Message bubble max-width: 75% of screen width

## Typography

| Role | Size | Weight | Line Height | Usage |
|------|------|--------|-------------|-------|
| Display | 28px | 700 | 1.2 | Screen titles ("Find housing", "New listing", "Messages") |
| Heading | 20px | 600 | 1.3 | Listing card title, chat header name, request card heading, section headers |
| Body | 16px | 400 | 1.5 | Message text, listing description, input field text, button labels |
| Label | 14px | 400 | 1.4 | Availability dates, distance/area text, city tags, unread counts, captions |

**Weight contract:** Regular (400) + Semibold (600) + Bold (700).

> **Weight-count override (Phase 1 parity):** 3 weights (400/600/700) intentionally retained. Bold 700 is a locked baseline from shipped Phase 1 screens (10 occurrences of `fontWeight: '700'` across `mobile/src/screens`). Reducing to 2 weights would break visual consistency with existing screens whose Display titles already render at 700. Visual debt accepted and documented per ui-checker override path.

Button labels use Body size (16px) at Semibold (600) — same as Phase 1 buttonText.

**Placeholders and muted text:** Label size (14px), weight 400, color `#999999`.

## Interaction Contracts

### Map discovery (LIST-03, LIST-04, LIST-05)

- `MapView` fills full screen behind a search bar overlay (top, floating, `#ffffff` + shadow)
- User location tracked via `expo-location` — blue dot on map
- Each listing is a `NeighbourhoodPin` at neighbourhood centroid — NOT exact coords until accepted
- Tap pin: shows listing summary sheet (half-height modal): photo, title, area, dates, "View listing" → `ListingDetailScreen`
- Filter FAB (bottom-right, 48×48dp): opens `FilterSheet` with date range
- Search bar accepts free-text city/area — triggers backend geocode + bounding-box query

### Listing detail (LIST-03, REQT-01, REQT-03)

**Guest — not yet accepted:**
- Hero photo carousel (full-width, 200dp tall; swipe left/right)
- Title (Heading/20px), host name + avatar, area label
- `SafetyChip` directly below area label — always visible to non-accepted guests
- Description, house rules, availability dates
- Sticky bottom bar: "Request stay" button (full-width, accent)

**Guest — accepted:**
- Same layout but `SafetyChip` replaced by `AddressRevealCard` (green, full address)

**Host viewing own listing:**
- No request button; shows "Manage listing" / "Remove listing" options

### Stay request compose (REQT-01)

- Pre-filled dates from listing availability
- `AvailabilityDatePicker` for exact check-in/check-out
- `TextInput` multiline for introductory message (max 500 chars, character count Label below)
- "Request stay" button disabled until both dates and message non-empty
- On submit: optimistic loading state on button ("Sending…", opacity 0.6); error inline below button

### Host inbox (REQT-02, REQT-03, REQT-04)

- `FlatList` of `RequestCard` components
- Accept: primary accent button → confirmation not required (irreversible in a positive direction)
- Decline: destructive red button → bottom sheet confirmation: "Decline this request? [Name] will be notified." → "Confirm decline" (red) / "Cancel" (text link)
- Accepted state: `RequestCard` shows "Accepted" green badge; no more action buttons
- Push notification delivered on both Accept and Decline (REQT-04)

### Direct messaging (MSG-01, MSG-02, MSG-03)

- `ConversationListScreen`: `FlatList` of rows (avatar + name + last message preview + timestamp + `UnreadBadge`)
- New DM: initiated from user profile ("Send message") — creates pending conversation
- `DirectMessageScreen`: header = recipient name + `OnlineIndicator`; message history `FlatList` (inverted); `ChatInput` fixed bottom
- First message in pending conversation: `MessageRequestBanner` shown above messages until accepted
- After acceptance: banner disappears, chat is fully open
- Real-time delivery via Socket.io room (`dm:{userId1}_{userId2}` deterministic room name)
- Optimistic send: message appears immediately with a "pending" indicator (clock icon, Label/14px); confirmed on server ack; failed state shows retry affordance ("tap to retry", #d32f2f text)

### City group chat (MSG-04, MSG-05)

- Joined automatically on first open if user has a `homeCity` set
- Socket.io room: `city:{citySlug}`
- UI identical to `DirectMessageScreen` but no `MessageRequestBanner`
- Header: "City: [City name]" + member count (Label/14px)
- No 1:1 actions in group chat (no accept/decline)

### Push notifications (MSG-05, REQT-04)

- All push events use Expo push service via EAS Build (noted as Phase 2 blocker in STATE.md)
- Notification tap → deep link to relevant screen (DM, group chat, or request inbox)
- Unread badges on bottom tab icons reflect real-time counts
