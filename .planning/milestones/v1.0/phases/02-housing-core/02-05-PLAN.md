<objective>
Deliver the city group chat slice end-to-end: a verified user opens the group chat for their home city, sees recent history, and exchanges real-time messages with every other member of that city; each new message push-notifies city members who are offline (not currently in the room). This is the final missing Phase 2 slice and completes MSG-04 plus the group-chat path of MSG-05 (02-04 already covers the 1:1 path). It satisfies ROADMAP success criterion 5.

Purpose: City group chat is the community backbone of a women-only platform. Its two security-critical properties are (1) a user may only participate in THEIR OWN city — the server derives the city from the caller's profile and never trusts a client-supplied slug, closing the unauthorized-room class of threats; and (2) group messages must never leak into 1:1 conversations or vice-versa. It reuses the authenticated socket from 02-01 and the Message model / chat components from 02-04 rather than recreating them.
Output: A citySlug on the User model (normalised on profile write), the Message model extended to a group scope, city REST endpoints, a store-first + server-gated city socket handler with offline-member push fan-out, and the mobile CityGroupChatScreen wired into the Messages tab.
</objective>

<design_notes>
Group-message storage decision (justified): REUSE the single `messages` collection created in 02-04 with a scope discriminator, rather than a second collection or an embedded array. A DM message carries `conversationId` + `type:'dm'` and no `citySlug`; a group message carries `citySlug` + `type:'group'` and no `conversationId`. This honours the locked "separate messages collection" decision (messages are still their own collection, never embedded), keeps 02-04's Message shape intact, and makes scope leakage structurally impossible: the city history query filters `{ citySlug, type:'group' }` and the DM history query filters `{ conversationId }`, so a message of one scope can never match the other's query. This matches RESEARCH Pattern 7 (Message with a `citySlug` field for group messages) and 02-RESEARCH Assumption A2 (city membership is implicit — no GroupChatMember collection).

City membership + authorization: city membership is derived from `User.homeCity` → `citySlug`. There is NO explicit join model. Per 02-RESEARCH Open Question 4, `citySlug` is normalised server-side on profile write: `homeCity.toLowerCase().trim().replace(/\s+/g,'-')`. The critical security rule for this slice: the socket handlers and REST endpoints ALWAYS derive `citySlug` from the authenticated user's own profile (`socket.data` / `req.user`), and NEVER accept a `citySlug` from the client payload. This single rule removes the entire "post in a city that is not yours" threat class — a client cannot fabricate a room name for a city it does not belong to.

Sender name for group bubbles (UI-SPEC "group message bubbles show sender"): the sender's `displayName` is resolved ONCE at join:city time and cached on `socket.data`, then denormalised onto each group Message (`senderName`) at create time. History reads therefore need no join, and MessageBubble gets an optional `senderName` prop it renders above non-own group bubbles. DM (02-04) passes no `senderName` and is unaffected.

Scope isolation on the client: the `message:new` payload carries the scope discriminator (`citySlug` for group, `conversationId` for dm). CityGroupChatScreen only appends events whose `citySlug` matches its own city; DirectMessageScreen (02-04) already scopes by conversation. Group messages go into a SEPARATE `cityMessages` store array, never the DM `activeMessages` array.
</design_notes>
